# Interview Journey Guidance

## Evidence-Based Answers

Interview preparation should separate confirmed facts, likely stage expectations, user assumptions, AI-generated suggestions, and missing information. A plausible question must be labelled as plausible, not guaranteed. Answers should link factual claims to Evidence Passport records, CV Evidence Lock claims, job requirements, projects, education, employment history, or user-confirmed facts.

Unsupported metrics should be softened until verified. For example, replace a precise unverified efficiency metric with a safer description such as reduced manual steps or improved workflow consistency. User confirmation can be stored separately from stronger external or project evidence.

## Recruiter Screening

Recruiter screening usually focuses on a concise introduction, motivation, availability, location, language, notice period, salary expectations if the user chooses to share them, and high-level role fit. Work authorisation, salary, or relocation details should only be used when the user has provided them. The system should not infer legal status or private constraints.

## Behavioural Interviews And STAR

A STAR story should include situation, task, action, result, and reflection. Quality checks should look for clear user ownership, specific actions, evidence-backed results, relevance, conciseness, confidentiality safety, and unsupported claims. The system may help structure a story, but it must not invent a complete fictional story.

## Technical And Portfolio Interviews

Technical preparation should use only the confirmed job stack, Evidence Passport records, user projects, current skill gaps, and Career Experiment results. Advanced questions that exceed demonstrated evidence should be labelled. Portfolio preparation should include problem, context, user need, the user's role, process, decisions, constraints, result, limitations, lessons learned, and what the user would improve.

## Case Interviews

Case practice can use deterministic templates such as improving a digital service, introducing AI into a manual workflow, designing an explainable recommendation feature, reducing drop-off, evaluating a RAG system, improving an application process, or planning a product feature. The workflow should cover problem understanding, clarifying questions, users, constraints, alternatives, trade-offs, risks, success indicators, and summary.

## Voice Privacy And Feedback

Voice mock interviews are optional. Text mode must remain available when voice is disabled or fails. Microphone consent is required before recording. Raw audio should not be permanently stored by default, transcripts should be saved only after user confirmation, and transcript deletion or correction must be supported. Voice must not be used for biometric identification, emotion detection, honesty detection, protected-attribute inference, or mental-health conclusions.

Feedback should evaluate only observable answer properties such as relevance, structure, clarity, evidence use, specificity, completeness, conciseness, role alignment, question coverage, uncertainty handling, unsupported claims, excessive jargon, reflection, and follow-up readiness. It should not create one opaque total score.

## Offer Discussion Limits

Offer review can organise confirmed offer facts, missing information, comparison with user priorities, clarifying questions, negotiation priorities, draft negotiation points, acceptance considerations, and unresolved risks. It must not provide definitive legal, tax, or financial advice unless verified official integrations exist.
